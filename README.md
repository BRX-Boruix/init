# init

BORUIX 的 **PID 1**——系统里第一个用户态进程，负责把系统从"内核已就绪"带到"可以使用"。

[English](README.en.md)

## 它做什么

| 阶段 | 工作 |
| --- | --- |
| 启动 | 按固定顺序拉起各个守护进程与硬件驱动 |
| 常驻 | 监督这些进程；需要时重新拉起 |
| 提供终端 | 为每个终端实例拉起终端守护进程与登录程序 |

## 启动顺序是有讲究的

顺序不是随意的，有一处硬约束：**音频输出设备是独占的**，[`audiod`](https://github.com/BRX-Boruix/audiod) 一旦认领就永不
释放。因此它必须**在 `intel-hda` 之后、且在任何其他想用该设备的程序之前**启动。

启动失败的守护进程**不阻断开机**——每个都是独立的，某一个起不来不影响其他部分。只有终端相关
的失败是严重的（没有终端就没有可用系统）。

## 终端实例

系统可以有多个终端，各自独立。实例数量在**构建时**注入，并与内核预创建的数量**同源同值**：

```
内核预创建几个终端实例 → init 就提供几个终端守护与几个切换位
```

这个数字必须一致，否则会出现"内核创建了但没人服务"或"有人服务但设备不存在"的情况。所以它
**只有一个真相来源**（构建期注入），并做防御性钳位。

## 两种会话模式

| 模式 | 行为 |
| --- | --- |
| **轮转**（默认） | 同一时刻只有一块终端在服务；一个会话结束后切换到下一块 |
| **并行** | 每块终端各自独立地同时提供服务 |

轮转是默认，因为它对内存和进程数的需求最小。并行模式适合需要同时使用多个终端的场景。

## 运行期新建终端

终端实例可以在运行时按需创建，方式是**文件协议**——请求方在约定的目录里创建一个文件，init 巡检
该目录并响应：

```
请求方创建 /system/console-requests/<n>   （n = 期望的终端编号）
init 扫描目录 → 校验编号 → 拉起该终端的守护与登录 → 登记 → 删除请求文件
```

**没有为此新增任何系统调用。** 请求文件的创建本身就有原子性，天然的重复请求去重也由此获得：
同名文件创建失败即表示"这个终端已经被请求过了"。

非法请求文件会被**如实删除并留下记录**，而不是静默忽略——丢弃是有意的裁决，必须可审计。

## 巡检不忙等

并行模式下 init 需要周期性醒来处理请求。它用**带超时的等待**实现：等待期内如果没有子进程状态
变化，超时即触发一次巡检。**超时期本身就是终端请求的最大响应延迟**（取 200 毫秒，交互可接受）。

## 构建

```bash
cargo build --release
```

可用的构建期选项：

| 选项 | 含义 | 默认 |
| --- | --- | --- |
| 终端实例数 | 开机预创建的终端数量，钳制在 1..=256 | 4 |
| 会话模式 | 轮转或并行 | 轮转 |

## 文件结构

```
init/
├── Cargo.toml    # 包定义
├── build.rs      # 注入链接脚本与构建期选项
├── linker.ld     # 用户态段布局
└── src/
    └── main.rs   # 启动序列、监督循环与终端实例管理
```
